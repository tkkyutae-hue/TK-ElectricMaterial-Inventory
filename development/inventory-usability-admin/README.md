# Admin 업무 처리 안내 — 실행 경로 밖 준비본

## 1. 확인한 문제와 보완

실행 앱에는 적용하지 않았다. `prepared/` 아래 파일은 전체 소스의
`.txt` 후보이며 자동 재시작·DB 호출을 일으키지 않는다.

| 소스에서 확인한 문제 | 준비본에서 한 일 |
|---|---|
| Dashboard의 조회 실패·미완료가 “정상 재고” 또는 무한 로딩처럼 보일 수 있음 | 기존 통계·부족 재고·카테고리 응답의 오류/로딩/빈 상태를 분리. 실패 때 정상 재고라고 표시하지 않음 |
| 재고 조회 오류가 빈 목록과 구별되지 않음 | 공통 `LoadState`를 재사용해 자료 없음·필터 결과 없음·연결 오류·권한 제한·명시적 기능 미설정 구분 |
| 재고 조회 hook이 HTTP 오류 상태를 버려 권한 안내를 구분하기 어려움 | 해당 읽기 hook 두 곳에서 상태/응답을 오류 객체에 유지. UI는 기술 문구를 그대로 출력하지 않음 |
| 재고 전체 상세를 거쳐 목록으로 돌아오면 필터가 초기화됨 | 검색·상태·분류·사용패턴·페이지·페이지 크기·정렬만 URL에 저장. 상세의 검증된 `returnTo`로 복귀 |
| 긴 규격·품목명이 재고 목록/상세에서 잘리거나 밀림 | 해당 텍스트 줄바꿈과 라벨 개선. 기존 표·빠른 보기·정렬·페이지 크기·사진·편집/삭제/이동/릴 기능은 유지 |
| 관리자 요청 상태 변경 결과가 토스트에만 남음 | 해당 요청 번호·현재 상태와 함께 처리 중/서버 확인/미적용/미확정 안내를 유지 |
| 처리 후 상태가 현재 필터 밖으로 바뀌면 결과를 놓칠 수 있음 | 방금 처리한 기록은 이유를 표시하고 같은 위치에 유지. 사용자가 필터를 직접 바꾸면 임시 고정을 해제 |
| 완료 상태에서 처리 컴포넌트가 사라져 결과와 Undo를 유지하기 어려움 | 관리자 처리 부분을 최종 상태에도 유지해 기존 완료 Undo를 기록 옆에 제공 |
| 미확정 재시도·권한·revision·부족 재고 안내가 기술 코드에 의존 | 기존 `requestCommand`/작업 ID/원래 revision/완료 원본 작업 ID를 그대로 사용하고 업무 안내로 표시 |

### 실제로 존재하는 업무 경로

- Admin Dashboard `/` → 기존 재고 `/inventory`와 구매/재주문 `/reorder`.
- 실제 자재 요청의 관리자 처리 버튼은
  `/field/transactions?tab=requests`의 **공유 요청 목록**에 있다.
  요청됨 → 준비 중 → 수령 준비 → 완료 및 기존 취소 경로만 유지했다.
  Dashboard 바로가기는 이 기존 경로를 연다. 새로운 Admin 승인 페이지,
  자재 “승인됨” 상태, 승인 단계, 집계는 만들지 않았다.
- `/admin/users`의 **계정 승인**은 자재 요청 승인과 다른 기능이다.
  이 작업에서 인증·계정 승인 정책/역할 부여 코드를 변경하지 않았다.
- 요청 화면의 실제 모드는 Field이므로 기존 공통 헤더가 Field 모드와
  현재 지점명을 표시하는 것은 유지한다. 관리자 역할을 Admin 모드라고
  잘못 표시하는 별도 헤더를 만들지 않았다.
- 요청 상세는 기존 카드의 펼침/접힘이다. 상태 필터를 URL에 유지하며
  필터로 잠시 숨기는 것만으로 열린 카드의 처리 안내를 폐기하지 않는다.

## 2. 검토할 파일

아래 경로는 모두 `prepared/client/src/` 기준이다.

| 후보 | 변경 범위 |
|---|---|
| `pages/Dashboard.tsx.txt` | 기존 상태별 요청 경로, 조회 범위 문구, 재고 관련 조회 상태와 긴 경고 품목명 |
| `pages/Inventory.tsx.txt` | 기존 핸들러/표 유지, 필터 URL·라벨·초기화, 조회 상태, 상세 복귀 링크 |
| `pages/ItemDetails.tsx.txt` | 선행 미디어 전체 준비본 유지, 허용된 목록 복귀, 조회 오류 안내, 긴 제목·상태 번역 |
| `pages/field/FieldRequestsList.tsx.txt` | **관리자 조건부 영역만**: 관리자 상태 필터, 결과 유지와 처리 컴포넌트 연결. Field의 자기 수정·자기 취소·초안·사진 로직은 선행 준비본 유지 |
| `components/admin/AdminRequestActions.tsx.txt` | 기존 관리자 상태 변경/완료 Undo의 기록별 안내. 별도 서버 저장소나 작업 ID 생성 체계 없음 |
| `components/admin/AdminLoadState.tsx.txt` | 기존 공통 상태 UI의 Admin 어댑터. 원시 오류 문구는 표시하지 않음 |
| `hooks/use-items.ts.txt` | 읽기 실패 시 상태/본문 유지. 쿼리·수량·쓰기 엔드포인트 변경 없음 |
| `hooks/use-dashboard.ts.txt` | 통계 읽기 실패 시 상태/본문 유지. 계산/집계 변경 없음 |
| `lib/i18n.ts.txt` | 선행 Field 문구를 그대로 두고 Admin 문구 EN/KO/ES만 추가 |

`manifest.json`은 후보/현재 실행 소스의 해시를 기록한다.
선행 공통 헤더·지점 표시·미디어 컴포넌트·Field 결과 안내 hook을
검증 작업본에서 재사용하며 다시 구현/수정하지 않았다.

구매가격·월별 가격 차트·RMS·출고/설치 수량 계산·일일보고서·라벨,
기존 재고 내보내기·자재 편집/삭제 저장 동작은 개편하지 않았다.
요청과 연결된 이동 기록의 직접 편집/삭제 제한도 그대로다.
따라서 `Transactions.tsx`, `ProjectDetail.tsx`를 수정할 이유가 없어
선행 미디어 준비본을 그대로 재사용했다.

## 3. 이번 검사와 전후 화면

최종 결과는 **후보 TypeScript 통과, 합성 브라우저 64개 경우 통과,
동일 조건 전후 36쌍, 브라우저 예외 0건, 예상하지 않은 외부/합성 요청
0건**이다. 전후 화면을 생성한 최종 실행은 후보 전체를 다시 겹친
작업본에서 검사했으며, 앞선 중간 작업본의 결과로 대신하지 않았다.
요청 처리 안내를 최종 상태에도 유지하고 필터 밖의 처리 기록을
보존하도록 보완한 뒤 최종 검사를 통과했다.

```sh
env -i PATH="$PATH" LANG=C.UTF-8 NODE_ENV=test \
  node development/inventory-usability-admin/verify.mjs
```

- 이미 설치된 의존성만 사용. 임시 디렉터리에 소스/설정 사본을 만들어
  선행 공통 → 미디어 → Field → 이번 Admin 후보 순으로 겹친다.
- 실제 앱 진입점·실제 인증 모듈·서버 모듈을 번들에 포함하지 않는다.
  환경을 비우고 HTTP/DNS/DB/리스너를 막은 하위 프로세스에서 타입 검사.
- 브라우저 문서는 `.invalid`의 합성 경로만 인라인 제공한다.
  브라우저 네트워크를 차단하고 `fetch`는 합성 자료/응답만 반환한다.
  서버·추가 포트·실제 로그인/DB/저장소를 사용하지 않는다.
- 실제 Dashboard/Inventory/전체 ItemDetails/공유 요청 카드,
  TanStack Query·기존 읽기 hook·기존 `apiRequest`·`branchFetch`·
  `requestCommand`·언어·테마·장바구니 provider를 사용한다.
  인증과 라우터 경계는 합성 fixture이며 실제 앱 전체 연결 검사가 아니다.
- 동일 자료·EN/KO/ES·밝음/어두움·390/1280 화면에서
  Dashboard·Inventory·펼친 관리자 요청 카드의 전후를 비교한다.
  **이전 화면도 선행 준비본을 겹친 기준**이며 실행 앱에 이미 반영됐다는
  뜻이 아니다.
- 이번 실행 결과는 `results.json`, 전후 화면은
  `generated-artifacts/inventory-usability-admin/comparison.html`.
  성공 기록은 테스트 완료 후에만 생성한다.
- `--checked-work=<분리 작업본>`은 전체 TS/TSX/JSON 입력 해시가
  동일한 경우에만 이미 통과한 타입 검사 재사용을 허용한다.
  후보가 바뀌면 재사용할 수 없다.

## 4. 보존한 경계와 남은 제한

서버 권한·상태 전이·예약/가용 재고 정의·수량 계산·revision·중복 저장
방지·지점/계정 격리는 바꾸지 않았다. 버튼 비표시는 서버 권한 검사를
대체하지 않는다. 기존 서버 검사 전체를 다시 실행하지 않았다.

공통 처리기가 **미확정 뒤의 권한 거절 등에서 원래 작업 ID를 버릴 수
있는 제한**은 선행 Field 작업에서 보고된 그대로다. 열린 화면에서는
이전 미확정을 실패로 바꾸지 않고 새 ID 재시도를 막는다. 그러나
패널/화면을 완전히 폐기하고 다시 열었을 때까지 보장하는 공통
pending/현재 권한 결과 확인 인터페이스는 없다. 이번 UI 범위에서
공통 로직을 몰래 재설계하지 않았다. 이 경로의 별도 보완/검토 없이
실제 업무에 활성화해도 안전하다고 주장하지 않는다.

실제 App/Wouter의 중첩 지점 라우터와 브라우저 뒤로/앞으로 이동 전체,
실제 휴대폰, 실제 로그인 뒤 역할별 업무 흐름은 이번 합성 경계 검사와
별개다. 기존 시작 설정 테스트 실패 1건도 해결했다고 주장하지 않는다.
실제 화면 이동 대기 시간은 측정하거나 해결하지 않았다.

## 5. 실제 연결에 남은 승인/설정

1. 이번 작업은 실행 소스·환경/포트/워크플로·DB·저장소·운영 배포를
   변경하지 않았다. 실제 반영은 미확정 작업 공통 경계를 먼저 검토한 뒤
   선행 준비본과 함께 별도 승인된 반영 절차로 해야 한다.
2. 기존 화면/초안/미확정 작업을 정리하는 절차 없이 직원 탭을 새로고침하거나
   지점을 전환하지 않는다. 공통의 새 문서 격리를 SPA 전환으로 대체하지 않는다.
3. 사진은 선행 미디어 준비본의 인증된 지점별 경로만 사용한다.
   실제 저장소 연결, 대상 bucket/provider/권한 확인, 과거 사진 반입은
   이번에 수행/승인된 것이 아니다. 구체적인 연결 목록과 보존 조건은
   `development/inventory-usability-media/README.md`를 그대로 따른다.
4. 실제 적용 시 대상 지점·허용 역할·합성 확인 범위·소스 적용/재시작
   허용 여부를 명시해야 한다. 기존 직원 자료를 화면 캡처용으로 읽지 않는다.
