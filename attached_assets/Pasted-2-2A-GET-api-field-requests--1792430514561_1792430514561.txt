2차 권한 보호 중 2A만 진행해라.

이번 승인 범위는 GET /api/field/requests의
‘계정 확인 실패 → 사용자 필터 누락 → 전체 요청 조회’
경로를 막는 최소 코드 수정과 격리 검증이다.

구매가격 보호 2B와 배정 PO 범위 제한 2C는 후속 작업으로 남긴다.
#620, Vite 설정 병합안, 공통 Select는 건드리지 마라.

1. 수정 범위

- 현재 계정을 정상적으로 확인했고 활성 상태임이 검증된 경우에만
  요청 목록 조회로 진행한다.
- 미로그인, 계정 삭제·비활성, 계정 조회 실패에서는
  요청 목록 저장소를 호출하기 전에 거절한다.
- 계정 미확인을 undefined 사용자 필터나 전체 조회로 변환하지 마라.
- 계정 조회 장애를 정상 200 응답이나 빈 목록 성공으로 숨기지 마라.
  오류 응답에는 DB 상세·SQL·비밀값을 포함하지 마라.
- staff의 본인 요청 조회에는 검증된 계정 ID를 사용한다.
  URL·쿼리의 사용자 ID로 타인의 요청이나 전체 목록을 조회할 수
  없도록 한다.
- 앞선 미들웨어가 남긴 사용자 객체가 있더라도 현재 계정 확인
  실패를 우회할 수 없도록 실제 실행 경로를 확인한다.
- admin/manager의 기존 정상 조회는 유지한다.
  manager_viewer 등 다른 역할의 기존 허용 범위는 소스로 확인하고,
  이번에 임의로 확대하거나 재정의하지 마라.

2. 기존 기능 보존

이번 문제를 막기 위해 요청 목록을 관리자 전용으로 바꾸지 마라.
staff는 계속 본인 요청 상태와 지급 결과를 확인할 수 있어야 한다.

기존 활성 계정 확인 기능을 안전하게 재사용할 수 있으면 재사용해라.
공용 인증 함수 전체를 무작정 변경해 다른 API까지 영향을 주지 마라.

요청 작성·수정·취소·Undo, 요청 operation 조회, 초안,
실제 재고 변경 권한과 저장 로직은 변경하지 않는다.
UI·디자인 변경은 하지 않는다.

3. 격리 검증

실제 수정 대상 라우트와 인증·조회 분기 코드를 사용하고,
계정 조회·요청 저장소·세션은 합성 데이터와 대역으로 분리한다.

필수 확인:

- 미로그인: 요청 목록 저장소 호출 없음.
- 삭제·비활성 계정: 요청 목록 저장소 호출 없음.
- 계정 조회 예외: 요청 목록 저장소 호출 없음.
- 이전 사용자 정보가 남아 있어도 최신 계정 확인 실패 시 거절.
- 정상 staff: 본인 ID로만 목록을 조회하고 기존 응답 기능 유지.
- staff가 다른 사용자 ID나 전체 조회를 요구해도 범위 확대 없음.
- 정상 admin/manager: 기존 허용된 조회 유지.
- 다른 기존 역할: 확인한 기존 정책보다 권한이 확대되지 않음.

여기서 ‘저장소 호출 없음’은 요청 목록·업무 데이터 조회를 뜻한다.
인증을 위한 합성 계정 조회와 혼동하지 마라.

가능하면 동일한 회귀 검사로 원본의 문제 경로와 수정 후 차단을
비교해라. 원본에서 문제를 확인한 조건과 수정안의 정상 조건을
구분하고, 검증 조건 개수를 수정한 오류 개수로 보고하지 마라.

4. 실행 제한

변경은 이번 서버 경로와 꼭 필요한 최소 helper·테스트로 제한한다.
기존 dev/prod DB, 업무 API, 실제 로그인·세션 저장소에는 접근하지 마라.

앱 시작·재시작, Preview 조작, 패키지 설치·업데이트,
DB 구조 변경, 데이터 수정, 커밋·push, 배포는 승인하지 않는다.

소스 변경이 자동 재시작 등으로 기존 실행 환경에 영향을 준다면,
실행 중인 소스 대신 분리된 임시 복사본에서 수정·검증하고
그 차이를 보고해라. 제한을 풀어서 실행하지 마라.
