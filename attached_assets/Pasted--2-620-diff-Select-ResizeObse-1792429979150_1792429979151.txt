2. 이미 구현한 보호는 유지

active admin/manager의 실제 재고 변경 권한과 staff의 요청 권한을
분리한 기존 구현을 먼저 확인해라. 이미 있는 보호를 다시 만들지 마라.

요청 카트, 작성 중 입력, 기존 초안, 요청 수정·취소 보호를 유지한다.
manager_viewer 등 기존 역할을 임의 삭제하거나 재정의하지 마라.

3. 이번에 확인할 조회 권한

A. 구매가격
- 구매단가·구매금액·공급사 견적은 admin/manager에게만 공개한다.
- 화면에서 숨기는 것으로 끝내지 말고 비RMS 재고·거래·프로젝트
  조회 응답의 중첩 객체와 집계값에도 가격이 남는지 확인해라.
- 실제 존재하는 가격 필드와 응답 경로를 소스로 확인해라.
- 일반 자재명, 규격, 재고량 등 정상 조회에 필요한 정보는 유지해라.
- RMS 구현과 견적 모듈 개편은 재개하지 마라.

B. 팀리더 조회 범위
- staff는 본인에게 배정된 PO의 업무와 본인 요청·실제 지급 결과를 본다.
- 같은 PO라도 다른 팀의 요청이나 전체 거래 이력이 함께 노출되지
  않도록 서버의 목록·상세·관련 조회 경로를 확인해라.
- URL이나 요청 ID, projectId를 바꿨을 때도 서버가 검사해야 한다.
- 기존 PO 배정 모델을 먼저 확인하고 새 배정 테이블을 임의로 만들지 마라.
- 배정 근거가 부족하면 그 부분만 차단사항으로 남기고,
  가격 비공개와 계정 확인 검토까지 함께 멈추지는 마라.

C. 계정 확인 실패
- 기존 세션이 있어도 비활성·삭제 계정은 보호된 업무 조회가 차단돼야 한다.
- 사용자 조회 실패나 역할 미확인을 전체 조회 권한으로 처리하지 마라.
- loadCurrentUser, loadRequestUser와 실제 호출 라우트를 함께 확인해라.
- 로그인 진입점 등 정상적인 공개 경로까지 무작정 차단하지 마라.

4. 첫 결과물

관련 API마다 아래 표를 만들어라.

API / 현재 인증·역할 검사 / 조회 범위 / 가격 포함 여부 /
이미 충족 또는 보완 필요 / 최소 변경 파일

현재 소스에서 확인한 사실과 아직 검증하지 않은 위험을 구분해라.
과거 테스트 실패를 현재 오류로 그대로 집계하지 마라.

그다음 합성 계정·합성 PO·합성 요청으로 검증할 계획을 제시해라.
실제 라우트·응답 처리 코드를 검사하되 DB와 세션 저장소는 격리한다.

필수 검증 사례:
- 정상 직원·팀리더의 필요한 조회는 유지된다.
- 다른 팀 요청·미배정 PO 접근은 거절된다.
- 구매가격이 허용되지 않은 역할의 응답에 남지 않는다.
- 계정 비활성·삭제·조회 실패가 전체 조회로 이어지지 않는다.
- admin/manager의 정상 업무와 기존 요청·초안 보호는 유지된다.

5. 이번 범위 밖

실제 재고·거래·릴 저장 로직, 반납 상한, 예약/FIFO, RMS,
데일리리포트 상세 설계, 디자인 개편은 변경하지 않는다.

기존 dev/prod DB 조회·쓰기, 업무 API 호출, 앱 시작·재시작,
패키지 변경, 배포는 하지 마라. 일부 GET과 앱 시작에도
자동 쓰기가 있을 수 있으므로 실행으로 확인하지 마라.

소스 대조표, 최소 수정안, 격리 검증 계획을 보고한 뒤
실제 수정 승인 전에는 멈춰라.
