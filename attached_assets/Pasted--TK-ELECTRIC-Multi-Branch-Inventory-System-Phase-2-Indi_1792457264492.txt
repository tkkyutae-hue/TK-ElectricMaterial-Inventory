# TK ELECTRIC — Multi-Branch Inventory System
## Phase 2: Indiana 독립 개발 환경 및 실제 Inventory 기능 연결

### 1. 작업 목표

Phase 1에서 구현한 지점 선택·권한 검사·공통 품목 구조를 기존 TK Electric Inventory에 연결하여, **Indiana Branch가 독립된 개발 환경에서 실제로 작동하도록 구축한다.**

이번 작업은 계획 작성이나 화면 시제품 제작으로 끝내지 않는다.

허용된 범위에서 **구현 → 격리 검사 → 문제 수정 → 통합 검증**까지 진행하고 결과를 한 번에 보고한다.

**최종 목표**

- 기존 TK Electric Inventory 소스 재사용
- Indiana 독립 개발 서버 및 PostgreSQL DB
- Indiana 전용 인증·세션·파일 저장소
- 로그인 → Indiana 선택 → Field/Admin Mode 선택
- 기존 Inventory 주요 업무 화면 연결
- Savannah 운영 환경 완전 격리
- Central Management는 Coming Soon 유지

기존 Inventory 기능을 처음부터 다시 개발하지 않는다.

### 3. 독립 개발 환경 확보

Indiana는 Savannah와 완전히 분리된 실행 환경이어야 한다.

다음 항목을 확인한다.

- Indiana 개발 서버
- Indiana 전용 PostgreSQL 개발 DB
- Indiana 세션 저장소
- Indiana 인증 설정
- Indiana Object/File Storage
- Indiana 개발 환경변수
- 외부 연동
- 백그라운드 작업과 예약 작업

**Indiana 서버가 Savannah DB나 세션 저장소를 참조할 가능성이 있으면 실행하지 않는다.**

Savannah 환경변수·비밀번호·토큰·세션·DB 연결 문자열을 통째로 복사하지 않는다.

Indiana에서 독립적으로 확인된 자원만 사용한다.

Monday.com, Jibble 등 외부 연동은 이번 개발에서 비활성화한다.

독립 설정이 없는 업로드·외부 API 기능은 실제 Savannah 자원에 연결하지 말고 개발 전용 대역으로 처리한다.

새로운 유료 인프라나 운영 자격증명이 필요하면 해당 부분만 차단사항으로 보고한다.

### 4. 서버 시작 전 자동 데이터 변경 차단

기존 Inventory 서버에는 시작 과정에서 다음 작업이 실행될 수 있다.

- Seed
- Schema Migration
- Backfill
- 외부 동기화
- Background Job

Indiana 환경에서 기존 서버 코드를 그대로 실행하기 전에 시작 경로를 확인한다.

다음 조건이 충족되어야 한다.

1. 모든 DB 연결이 Indiana 독립 개발 자원을 가리킨다.
2. Savannah DB와 연결되는 설정이 없다.
3. 테스트 단계에서 자동 seed/migration/backfill이 임의의 기존 데이터를 변경하지 않는다.
4. 외부 동기화와 업무 연동은 비활성화되어 있다.
5. 실행 대상이 기존 Savannah 개발·운영 서버가 아니다.

기동에 필요한 초기 스키마는 Indiana 신규 개발 DB에 한해서 명시적으로 적용하고, 실제 변경 대상과 실행 로그를 기록한다.

기존 Savannah DB 마이그레이션은 절대 실행하지 않는다.

독립성 확인이 불가능하면 서버 실행을 중단하고, 나머지 소스·합성 검증을 계속 진행한다.

기존 컴포넌트·라우트·서비스·DB 모델을 재사용한다.

공통 기능을 Indiana 전용으로 다시 작성하지 않는다.

Indiana 전용 차이는 환경 설정으로 관리한다.

현재 기존 코드에 존재하는 기능과 실제 운영 적용된 기능, 검증되지 않은 기능을 구분한다.

이번 작업에서 기존 재고·릴·요청·Undo 로직을 불필요하게 재설계하지 않는다.

### 6. 로그인 및 지점·모드 선택 연결

Indiana 독립 개발 환경에서 다음 흐름을 구현한다.

**Login → Select Workspace → Indiana → Select Mode → 기존 Inventory 화면**

Branch Selection 항목:

- Indiana — 개발 환경에서 작동
- Savannah — Not Connected
- Central Management — Coming Soon

요구사항:

- 기존 로그인 UI를 재사용한다.
- 기존 인증·권한 구조와 호환되도록 개발한다.
- Indiana 전용 인증·세션 저장소를 사용한다.
- 기존 Savannah 계정·비밀번호·세션 DB는 복사하지 않는다.
- 회사 Google 로그인 연동에 별도 인증 설정이 필요하면 Savannah의 OAuth 비밀값을 복사하지 말고 독립 설정 여부를 먼저 확인한다.
- 독립 Google 로그인 설정이 준비되지 않았다면 개발용 합성 계정으로 흐름을 검증하고 실제 로그인은 미완료로 보고한다.
- 실제 지점 접근권한과 모드 접근권한을 서버에서 검증한다.
- URL이나 branch ID 변경만으로 접근권한을 얻지 못한다.
- Savannah 항목은 실제 Savannah API·인증·DB를 호출하지 않는다.
- Central Management는 실제 CRUD 없이 Coming Soon만 표시한다.
- 다른 계정이나 지점의 캐시·초안·작성 중 요청·장바구니가 섞이지 않도록 한다.

실제 SSO가 구현되지 않았다면 로그인 통합 완료라고 주장하지 않는다.

### 7. Indiana 데이터 초기화 기준

이번 Phase 2의 검증에는 **합성 품목과 독립 개발 데이터만 사용**한다.

실제 Savannah 자재목록을 임의로 가져오지 않는다.

Indiana 초기 상태는 다음과 같다.

| 항목 | 초기 상태 |
|---|---|
| Inventory Items | 합성 품목, 수량 0 |
| Location Balances | 0 |
| Wire Reels | 실물 기록 없음 |
| Inventory Movements | 기록 없음 |
| Material Requests / Drafts | 기록 없음 |
| Reservations | 없음 |
| Projects / PO | 실제 업무기록 없음 |
| Purchase Prices | Savannah 구매가격 미복사 |

테스트용 계정과 필요한 기준 카테고리·창고 위치는 합성 데이터로 생성할 수 있다.

초기 상태 검증과 업무 시나리오 검증은 서로 다른 독립 테스트 데이터에서 수행한다.

거래 검사를 실행한 뒤 수량만 다시 0으로 바꾸거나 이력을 삭제하여 초기 상태로 위장하지 않는다.

실제 운영 품목·사진 도입은 다음 단계로 보류한다.

### 8. 공통 품목 표준화 구조 유지

Phase 1에서 준비한 다음 구조를 유지한다.

- Global Master Item ID
- Local Item ID
- Standard SKU
- Standard Item Name
- Category / Specification
- Size
- Unit of Measure
- Catalog Version
- Allowed Sync Fields

이번에는 실제 Central Master DB나 자동 동기화 서비스를 구현하지 않는다.

Global Master Item ID와 지점 Local Item ID를 혼동하지 않는다.

향후 중앙에서 승인된 SKU·자재명·규격·사이즈 변경이 모든 지점에 전파될 수 있도록 기존 인터페이스를 보존한다.

중앙 품목 변경이 재고 수량·가격·릴·거래·PO·초안을 덮어쓰지 않도록 한다.

### 9. 공통 코드베이스 및 버전 관리

**One Shared Codebase, Independent Branch Deployments.**

Indiana는 기존 TK Electric Inventory의 동일한 코드베이스에서 빌드되어야 한다.

요구사항:

- 공통 UI·업무 로직의 단일 원본 유지
- 지점별 차이는 설정으로 분리
- Indiana 기준 커밋과 변경 내역 기록
- 공통 코드 변경 시 별도 재개발 없이 Indiana에 적용 가능
- Savannah와 Indiana의 서버·DB·세션은 독립
- 지점별 배포는 독립적으로 검증하고 승인

기존 GitHub main에 자동 push·merge하지 않는다.

코드 공유가 단순한 일회성 복사에 그친다면, 이를 공통 코드 관리 완료로 보고하지 않는다.

기존 Repository와 안전하게 연결할 수 없는 경우에는 검증된 별도 개발 작업본과 통합 가능한 diff를 제공한다.

### 10. 통합 검증

다음 항목을 검증한다.

**A. 환경 격리**
- Indiana DB가 Savannah DB와 다른 독립 자원인지 확인
- 세션·파일 저장소·외부 연동 분리
- Savannah 업무 API 호출 없음
- 외부 자동 동기화 비활성화

**B. 로그인·권한**
- 로그인 → Indiana → Mode 선택 → 화면 진입
- 정상 역할별 모드 접근
- 미인증·권한 없는 역할 거절
- Savannah 미연결 동작
- Central Coming Soon 동작
- 사용자·지점 간 세션/캐시 혼동 없음

**C. 기존 화면·기능**
- 기존 Admin Mode / Field Mode 렌더링
- 자재 검색·상세·필터·카테고리
- 입고·출고·반납 UI
- 거래 이력 UI
- 릴 화면과 요청 화면
- 한국어·영어·스페인어
- Light / Dark Theme
- 모바일·데스크톱

**D. DB·수량 보호**
- 초기 합성 품목 재고 0
- 위치별 재고 0
- 초기 릴·거래·요청·초안 없음
- 독립된 폐기용 데이터에서 실제 입출고 시나리오 실행
- 기존 Savannah 수량·가격·거래 이력 접근 없음

브라우저 검사는 가능하면 실제 Indiana 개발 환경을 사용하되, 독립성과 데이터 안전성이 확인된 경우에만 진행한다.

독립성이 확인되지 않았다면 모든 업무 네트워크를 차단한 합성 브라우저 검사로 대체하고 실제 서버 검증 완료라고 표현하지 않는다.

### 12. 실행·승인 범위

이번 작업에서는 **Indiana 독립 개발 환경의 구현과 합성 데이터 검증**을 허용한다.

독립성이 확인된 신규 Indiana 개발 DB에 대해서는 필요한 스키마와 합성 기준정보를 구성할 수 있다.

그러나 기존 Savannah 또는 다른 운영 DB에 접근하거나 변경해서는 안 된다.

기존 Savannah 프로젝트의 실행 파일과 설정은 변경하지 않는다.

기존 앱을 시작하거나 재시작하지 않는다.

기존 GitHub main에 자동 push하거나 운영 배포하지 않는다.

새 유료 인프라·외부 인증 설정이 필요할 경우 해당 부분만 승인 대기로 남기고 독립적으로 가능한 작업은 계속 진행한다.

승인 범위 안에서 발견한 문제는 수정하고 필요한 회귀 검사까지 수행한다.

기술적인 세부사항마다 중간 승인 요청을 반복하지 않는다.
