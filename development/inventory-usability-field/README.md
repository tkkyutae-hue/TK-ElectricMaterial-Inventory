# Field 검색·수량 입력·요청 결과 안내 준비본

## 반영 상태

**실행 앱에는 반영하지 않았다.** `prepared/`의 `.txt`는 기존 소스에 대응하는
전체 후보다. 자동 적용·실제 앱/Preview 접근·직원 로그인·DB/저장소 접근·
환경/패키지 변경·서버 시작/재시작·배포를 하지 않았다.

비교 기준은 **앞선 공통/미디어 준비본을 조합한 분리 작업본**이다.
앞선 준비본이 실제 앱에 활성화되었다는 뜻이 아니다. 이 작업의 준비본은
그 미디어 변경을 유지하고 Field 관련 부분만 덧붙인다.

## 1. 확인한 불편과 수정

| 원본에서 확인한 부분 | 이번 후보 변경 |
|---|---|
| 검색/필터는 있지만 일부 접근 가능한 이름과 필터 칩의 조건명 부족 | 기존 검색·필터·프리셋·초기화/URL 처리에 라벨·선택 조건 설명만 추가 |
| 일부 빈 결과 문구에 다음 동작이 부족 | 선행 `LoadState`로 검색/필터 결과 없음과 전체 자료 없음을 구분하고 기존 초기화 연결 |
| 긴 이름/규격이 생략되거나 수량 조작 부분에 붙음 | 목록·상세·장바구니·인라인 수정에서 줄바꿈/최소 너비/조작 영역 배치 보완 |
| 수량은 기존 규칙대로 보정되지만 이유를 알기 어려움 | 기존 정수·최소 1·숫자 제거/parseInt 보정 규칙은 유지하고 단위·라벨·해당 항목 안내 추가 |
| 고정 카트 바 아래 여백이 실제 줄 수에 대응하지 못함 | 실제 높이를 측정해 예약. 모바일 키보드가 나타난 경우 바를 숨김 |
| 모바일 패널의 고정 vh가 키보드에 가려질 수 있음 | 실제 visualViewport 높이/하단 위치에 맞춰 독립 스크롤 영역 확보 |
| 작성/처리/성공/실패가 주로 토스트에만 남음 | 폼·요청 기록 주변에 작성 중, 처리 중, 서버 확인, 적용 안 됨, 결과 확인 중 안내 |
| 버튼 렌더링 전 빠른 재클릭과 미확정 중 값 변경 | 동기 잠금, 처리/미확정 중 기존 의도 유지, 같은 명령 경로의 명시적 재시도 |
| 닫힌 패널의 늦은 성공/세션 종료 뒤 응답이 혼동될 위험 | 화면 수명과 진행 중 작업 수명을 구분. 정상 완료는 제출한 초안만 정리하고 세션 종료 응답은 버림 |
| 밝은 테마 카트 바/요청자 선택기의 색상이 고정 | 기존 Field 테마 토큰/현재 테마 사용 |

수량 공식, 현재고·예약·가용량 정의, 재고 변경 시점, 요청 업무 상태,
작업 ID 생성/서버 중복 방지, 캐시/초안 저장 방식, 필터 검색 규칙을
새로 만들지 않는다. 기존 URL·페이지·필터·장바구니 정책을 유지한다.

## 2. 파일별 검토 목록

- `pages/field/FieldInventory.tsx`: 기존 미디어 연결을 보존한 목록/필터/
  상세 수량/하단 바의 제한적 수정.
- `pages/field/FieldCartPanel.tsx`: 패널 높이·스크롤·닫기 라벨/초안 안내.
- `pages/field/FieldCartReview.tsx`: 긴 품목 정보/단위·입력 보정 안내,
  제출과 Undo의 폼 주변 안내, 잠금, 제출한 초안만 정리하는 기존 호출 유지.
- `pages/field/FieldRequestsList.tsx`: 본인 요청 인라인 수정/취소 결과를
  해당 기록에 표시. 관리자 승인/준비/출고/삭제 처리의 개편은 다음 범위다.
- `pages/field/FieldCommandFeedback.tsx`: Field 내 표시·동기 잠금·작업 수명
  보호를 위한 작은 로컬 보조 코드. 요청/receipt/operation ID/payload나
  초안을 생성·저장하지 않으며 전역 상태 저장소를 추가하지 않는다.
- `lib/i18n.ts`: 위 변경에 필요한 문구만 기존 EN/KO/ES 사전에 추가.

`FieldMovement`, `FieldTransactions`, `requestCommands`, `RequestWorkflowNotice`,
서버/권한, 선행 공통 헤더/로그인/미디어 로직은 수정하지 않았다.
`manifest.json`은 후보와 대응 실행 파일의 기준 해시를 제공한다.
실제 적용 전 기준이 바뀌었다면 전체 파일을 덮어쓰지 말고 차이를 검토해야 한다.

## 3. 재사용/연결 의존성

- 공통 지점/모드 표시는 선행 Field layout 소유다. 이 화면에서 중복 표시나
  새 지점 선택을 만들지 않는다.
- `development/inventory-usability-common`의 `LoadState`, 공통 언어/상태
  표시가 필요하다.
- `development/inventory-usability-media`의 `BranchMediaImage`,
  `BranchItemGallery`, 요청 첨부 연결과 기존 인증 경로를 그대로 재사용한다.
- 요청은 기존 `requestCommand`만 호출한다. 미확정 중 새 작업 ID를 만들거나
  다른 payload로 결과 확인을 대신하지 않는다.

## 4. 검사와 비교 화면

최종 결과: 후보 TypeScript 통과, **51개 합성 브라우저 경우 통과**,
동일 조건 전후 화면 **24쌍**, 브라우저 예외 및 예상하지 않은 외부 요청
각각 0건. 대응 실행 파일의 해시가 바뀌지 않았음도 확인했다.
범위가 같은 타입/캡처는 소스 입력이 동일한 분리 작업본과 대조해 재사용했으며,
테스트 경계의 React 모듈 해석과 공통 번역 버튼 선택자 오류를 고친 뒤
최종 결과를 기록했다. 이 검사 도구의 오류를 실제 앱 장애로 계산하지 않는다.

```sh
env -i PATH="$PATH" LANG=C.UTF-8 NODE_ENV=test \
  node development/inventory-usability-field/verify.mjs
```

이전 준비본과 이번 후보를 `/tmp` 분리 작업본에 조합한다. 자격증명을
상속하지 않고, 타입 검사는 기존 오프라인 가드 아래 실행한다.
브라우저는 실제 변경 컴포넌트·언어/테마 공급자·카트 provider/store·
`requestCommand`·`branchTransport`를 사용하되 인증·라우터·조회/저장 경계를
합성 자료와 모의 응답으로 대체한다. 기존 설치 패키지만 사용한다.

기존 격리 검사 방식인 Chromium의 합성 `.invalid` 문서와 네트워크 차단을
재사용하며 HTTP 서버나 포트를 열지 않는다. 전체 서버/SQL/권한 검사 묶음은
반복하지 않는다. 실제 작업 ID의 재사용은 모의 응답에 보내진 envelope로
검사하는 것이며, PostgreSQL 트랜잭션/실제 계정 권한의 새 증명이 아니다.

- 최신 경우 수/시나리오: `results.json`.
- 타입 결과: `generated-artifacts/inventory-usability-field/typecheck.log`.
- 전후 화면: `generated-artifacts/inventory-usability-field/comparison.html`.
- 같은 합성 품목/자료, EN/KO/ES, 밝은/어두운 테마, 390/1280px의
  카트와 자재 목록을 동일 조건으로 비교한다.
- 기존 통과 결과나 반복 실행 횟수를 이번 검사 수에 합산하지 않는다.

## 5. 공통 로직에 남은 구체적 제한

범위를 확대해 공통 요청 처리기를 변경하지 않았다.

1. 현재 공통 처리기는 미확정 재시도의 후속 `FORBIDDEN` 등 일부 거절을
   확정 실패로 취급하고 메모리의 원래 작업 ID를 제거할 수 있다.
   Field 후보는 이미 미확정이었던 작업을 이 거절만으로 실패라고 바꾸지
   않고 새 ID 재시도를 막는다. 이 상태는 관리자 확인이 필요하다.
   이 차단은 열린 화면의 로컬 안내이며, 패널을 닫거나 화면을 떠나 그
   안내가 폐기된 뒤에도 보호한다고 주장하지 않는다. 공통 처리기의 ID가
   사라진 경우에는 재진입 후 같은 초안의 새 제출 위험이 남는다.
   따라서 이 미확정→권한 거절 경로의 공통 보완/확인 없이 준비본을
   실제 업무에 활성화해도 안전하다고 보지 않는다.
   공통 처리기의 정책을 바꾸려면 별도 범위에서 원래 ID/의도 보존과
   현재 권한으로 제한된 결과 확인 인터페이스를 함께 검토해야 한다.
2. 처리기의 메모리 pending 정보에 읽기용 인터페이스가 없어 패널을 다시
   열었을 때 미확정 상태/원래 의도를 미리 복원할 수 없다.
   기존 초안은 보존되고 다른 의도의 제출은 기존 처리기가 차단하지만,
   화면 재진입 직후의 표시까지 영속적으로 복원했다고 주장하지 않는다.
   임의의 전역 저장소나 개인 초안 영구 저장으로 우회하지 않았다.
3. 처리기의 성공 응답 검증은 operation ID와 revision 중심이다.
   전체 응답 스키마 검증을 이번 UI 작업에서 재설계하지 않았다.
4. 실제 휴대폰 키보드/브라우저 주소창, 실제 로그인 후 역할별 업무 흐름은
   합성 visualViewport/컴포넌트 검사와 별개로 확인해야 한다.

## 6. 실제 연결에 남은 설정/승인

이번 Field 작업에는 신규 환경 설정이 없다. 실행 코드 적용/자동 갱신
시간의 승인과 함께 앞선 공통·미디어 준비본을 조합 검토해야 한다.
사진의 실제 연결은 이전 미디어 준비본 README에 기록된 대상 지점 매핑,
비공개 저장소/루트 설정과 접근 권한, 실제 파일 작업의 명시적 승인이
여전히 필요하다. 여기서는 현재 설정값을 조회하거나 실제 파일을 조작하지
않았으므로 설정되어 있다/없다고 단정하지 않는다.

**기존 시작 설정 테스트 실패, 실제 로그인 업무 흐름 미검증, 실제 화면 이동
대기시간의 원인·해결은 별도 미해결로 남는다.**
