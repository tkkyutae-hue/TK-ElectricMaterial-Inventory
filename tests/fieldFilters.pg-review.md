# 필드 필터 실제 PostgreSQL 검증 결과

## 결론

- 실제 SQL 정확도: **15 통과 / 0 실패**.
- 실제 페이지의 카테고리 전환·해제 시 브랜드 초기화: **1 통과 / 0 실패**.
  이 브라우저 검사는 실제 컴포넌트와 모의 HTTP 응답을 사용했으며 PostgreSQL과 연결하지 않았다.
- 성능 조건 16개 중 **12개 정상 측정 / 4개 조회 실패**.
  정상 조건마다 준비 실행 1회 후 3회 측정했다. 실패 조건은 첫 실행에서 중단했다.
- 활성 품목 80,000개에서 품목/규격 조회 모두 `08P01` 바인딩 오류.
  검증 명령의 종료 코드 1은 이 발견을 반영한다. 실패를 숨기거나 업무 코드를 수정하지 않았다.

## 안전 범위와 실제 실행 경로

`tests/fieldFilters.postgres.ts`와 `tests/helpers/disposableFieldPg.ts`를 추가했다.
현재 `server/storage.ts`를 메모리에서 번들링하고 `./db` import만 새 테스트 DB로 대체했다.
실제 저장소 메서드 → Drizzle → node-postgres → PostgreSQL 16.10 경로로 SQL을 실행했다.
SQL 정확도 검사에서는 DB 반환값을 흉내 내지 않았다.

새 임시 디렉터리에 initdb를 실행했으며, TCP 수신은 비활성화했다.
권한 0700의 전용 Unix 소켓으로만 연결했다. 기존 DB 연결정보·환경 비밀값을 사용하지 않았다.
연결 후 data_directory가 직접 만든 경로인지, public 테이블이 없는 새 DB인지 확인한 뒤에만
합성 테이블과 데이터를 생성했다. 앱 조회용 연결은 read-only와 statement timeout을 적용했다.
기존 앱·마이그레이션·시드·동기화·인증 서비스를 부팅하거나 호출하지 않았다.
검증 후 **테스트 PostgreSQL 종료와 전용 임시 디렉터리 삭제가 완료**됐다.

조회에 필요한 7개 테이블의 열 타입·기본값·PK·unique 제약을 현재 스키마 정의에서 구성했다.
관련 없는 업무 테이블로 연결되는 FK는 테스트 DB에서 생략했다. 전체 운영 스키마 복제나
마이그레이션 검증은 아니다. 기존 스키마 파일·인덱스에는 변경이 없다.

## 합성 데이터와 정확도 검사

정확도 데이터: 품목 10개(활성 9), 카테고리 4개, 창고 2개, 브랜드 2개,
릴 5개(활성 3), 이미지 경로 1개, 창고 잔액 2개. 개인정보·실데이터 복제 없음.

검증한 내용:
- 활성 여부, 카테고리, 브랜드, 브랜드 후보 개수.
- 브랜드별 하위분류·규격 후보와 품목 결과 일치.
- 이름/SKU/규격/설명 및 복수 검색어, 결과 없음.
- 최소재고 기준과 reorderPoint 구분, 활성 릴 합산, 비활성 릴 제외.
- 재고 0, 길이 0인 활성 릴, 발주 상태, 비활성 릴만 있을 때 기존 품목 수량 사용.
- 카테고리/품목군/유형/브랜드/하위분류/검색/상태/규격의 결합.
- 페이지별 total 동일성, 누락·중복 없는 페이지 합집합, 규격 후보는 페이지와 선택 규격에 종속되지 않음.
- 기존 이미지 경로 부착, 위치 누락 시 null 처리, 읽기 전용 연결 상태.

### 창고 해석

현재 필드 목록에는 창고별 수량 필터가 없고, 품목 전체 수량 또는 모든 창고의 활성 릴 합계를 사용한다.
창고 1 잔액 0 / 창고 2 잔액 4인 합성 품목에서 목록 수량 4를 확인했다.
두 창고에 분산된 활성 릴 1+1은 전체 수량 2로 표시됐다.
이것은 현행 전사 수량 규칙의 검증이지 창고 간 혼입 결함의 증거가 아니다.
다른 창고별 API·잔액 일치·운영 과거 데이터는 검사하지 않았다.

## 규모별 측정

환경: Linux x64, Xeon Platinum 8581C 2.30GHz, 관측 논리 CPU 8개, 호스트 메모리 약 15.64 GiB.
공유 컨테이너이므로 전용 CPU/메모리 할당량이나 운영 장비 성능을 의미하지 않는다.
새 PostgreSQL 16.10, shared_buffers 64 MB, 로컬 Unix 소켓, 단일 동시 실행.
브라우저 검사는 성능 측정 종료 후에 실행했다.

활성 품목 1,000 / 10,000 / 50,000 / 80,000개. 카테고리 4개,
카테고리별 브랜드 2개, 규격 8개, 하위분류 3개. 최소재고 5.
저장 수량은 20개당 0~5가 각 1개, 나머지 14개는 100.
1,000번째마다 발주 상태, 위치 누락 10%, 성능 데이터의 이미지는 0개다.
릴 포함 조건에서는 품목 5개마다 릴 4개(활성 3 / 비활성 1).
릴 관리 품목의 절반은 활성 합계 0, 나머지는 6이다.

모든 측정은 category=1, brand=A, search=Synthetic, page=1, perPage=10 조건이다.
정상 실행마다 total=전체 품목수/8, 반환 품목 10개, 규격 8개도 검증했다.

### 릴 집계 비용 해석

규격 경로의 릴 SQL 왕복 평균(ms), 릴 없음 → 있음:
- 1,000품목: 1.31 → 2.30
- 10,000품목: 16.77 → 20.10
- 50,000품목: 88.89 → 83.18

릴 없음 조건도 **현재 코드의 집계 쿼리를 실행한다**. 이전 버전과 비교한 측정은 아니다.
캐시·계획·GC·공유 장비 편차가 있고, 전체 시간의 증가도 일관되지 않아 릴 행 증가만을
주 병목으로 확정할 수 없다. 쿼리 왕복에는 전송·디코딩이 포함되며 PostgreSQL 서버 실행시간
단독 측정도 아니다. ORM 쿼리 생성·결과 변환·분류·정렬 등의 비용도 전체 시간에 포함된다.
50,000품목에서 필터 결과 6,250개 중 10개만 표시하더라도 조회 전체는 약 3초 이상 걸렸다.

## 확인된 실패와 최소 수정 제안 — 아직 적용하지 않음

활성 품목 전체를 먼저 읽고 모든 ID를 후속 IN 조건에 넣는다.
80,000품목에서 실제 실패 단계:
- 품목: item_images 조회, 매개변수 **80,000개**, `08P01`.
- 규격: wire_reels 집계, 매개변수 **80,001개**, `08P01`.

릴 0개·이미지 0개인 경우에도 발생했다. 이는 해당 테이블의 데이터 양 때문만이 아니라,
전체 ID를 한 번에 바인딩하는 경로의 실패다. 실제 운영 규모나 운영 장애 발생 여부는 미확인이다.
정확한 경계 개수는 이번 검사에서 별도로 찾지 않았다.

승인 후 최소 수정 후보:
1. 대량 ID IN을 하나의 타입 지정 배열 조건 또는 적절한 조인으로 바꾸어 바인딩 폭증을 차단.
   shared liveReelQtyMap의 다른 호출 경로도 회귀 검증해야 한다.
2. 단순 카테고리·브랜드 등 의미를 유지할 수 있는 조건을 앞단 SQL에 적용해 읽는 범위를 축소.
   이름 파생 분류·검색·릴 재고·정렬·total 의미는 바꾸지 않고 합성 결과로 비교해야 한다.
   현재 단계에서는 업무 코드·인덱스·스키마 수정 없음.

## 미검증 및 보존

- 전체 HTTP/인증, 원격 DB 드라이버·네트워크, 실제 모바일/Safari, 운영 데이터, 동시 쓰기,
  다중 사용자 부하, 이미지가 많은 경우, SQL EXPLAIN/실행계획별 원인 분석은 미검증.
- UI 초기화 1건은 실제 페이지+모의 응답으로 별도 실행했으며 SQL-브라우저 통합 검사는 아니다.
- 업무 코드, 1·2단계 보호, 선택창 진단, 공통 Select/레이아웃, 디자인 시안,
  설정·패키지·인증정보·기존 DB·배포를 변경하지 않았다.
- 기존 Start application 실행·재시작·중지는 요청하거나 수행하지 않았다.
- 이 수치는 합성 데이터·공유 개발 장비의 검사 기록이며 **운영 성능 보장이 아니다**.
