# 공통 작업 ID 보존 — 실행 앱 미반영 준비본

## 반영 상태

**실행 앱에는 적용하지 않았다.** `prepared/`의 `.txt`는 전체 소스 후보다.
기존 실행 소스, 서버, DB, 실제 로그인·세션·저장소, 비밀값, 패키지,
환경·포트·워크플로, GitHub 원격 및 배포를 변경하거나 사용하지 않았다.
실제 앱/Preview를 열거나 서버를 시작·재시작하지 않았다.

타입 검사용 일회용 작업본에서만 공통 → 미디어 → Field → Admin →
이번 후보 순으로 소스를 겹친다. **이는 네 준비본의 최종 통합·실제
라우터 연결 검사가 완료됐다는 뜻이 아니다.**

## 1. 확인한 문제와 공통 계약

기존 공통 처리기는 결과 미확정 후의 재시도가 `FORBIDDEN` 등의 오류를
반환하면 원래 작업 ID를 지울 수 있었다. 패널이 폐기되면 UI의 로컬
차단도 사라져, 앞선 요청이 실제 저장됐어도 새 ID로 제출할 위험이 있었다.

이번 후보의 원칙:

| 상황 | 처리 |
|---|---|
| 최초 시도에서 기존 확정 거절 코드 반환 | 기존 분류대로 대상 잠금 해제. 이번 작업의 미확정 이력은 없음 |
| 전송/응답/본문 검증 결과 미확정 | 원래 ID, 복제한 원래 본문, revision, 완료 원본 ID 유지 |
| 미확정 이후 권한·인증·충돌·재고 등의 후속 오류 | 앞선 실패의 증거로 사용하지 않음. 원래 ID와 의도 유지 |
| 같은 의도의 동시 호출 | 진행 중인 한 Promise/한 쓰기 공유 |
| 같은 대상에 다른 의도 | 새 ID 발급·새 쓰기 차단 |
| 명시적 결과 확인 | 기존 GET 작업 결과 API를 현재 권한으로 호출 |
| `committed`이고 원래 ID/대상/revision이 유효 | 서버 확인 결과만 반환. 재전송 없이 pending 해제 |
| `unknown` | 실패 증거가 아님. 쓰기 재시도가 허용될 때만 원래 의도로 같은 ID 재시도 |
| 미확정 후 권한/인증/지점 선택 거절 이력 있음 | 이후 확인은 GET만 허용. `unknown`이면 쓰기 재개하지 않음 |
| 결과 확인 접근 거절 | 과거 서버 응답 복원 없음. 미확정 유지, 새 제출 차단 |
| 세션 종료/계정 교체 | 기존 transport가 문서를 영구 무효화. 사적 의도 제거, 지연 응답 폐기, 이 문서의 새 쓰기 거부 |

거절 뒤에도 현재 권한으로 확인 가능한 `committed` 결과는 확인할 수
있다. 결과가 없거나 계속 조회 불가하면 관리자의 업무 확인이 필요하다.
일정 시간이 지났다는 이유로 잠금을 풀거나 새 ID로 바꾸는 기능은 없다.
후속 `COMMAND_ROLLED_BACK`도 앞선 미확정 이력을 임의로 지우지 않는
보수적 정책이다.

기존 서버의 중복 방지, 현재 권한 검사, 삭제 확인의 최소 응답은
변경하지 않았다. 과거 성공은 현재 본문 조회 권한이 아니다.
삭제 결과는 ID·revision·삭제 여부만 반환한다.

## 2. 준비 파일과 재사용 인터페이스

모든 경로는 `prepared/client/src/` 기준이다.

| 파일 | 변경 |
|---|---|
| `lib/branchTransport.ts.txt` | 기존 문서 지점·계정·세대·무효화 규칙을 읽는 공통 context getter만 추가. 라우팅/인증 정책 변경 없음 |
| `lib/requestCommands.ts.txt` | 기존 한 메모리 pending 소유자 확장. 원래 의도 복제, 미확정 이력 보존, 결과 확인 후 동일 ID 재시도, 수명/응답 검증 |
| `pages/field/FieldCommandFeedback.tsx.txt` | 공통 pending 구독·재진입 표시·명시적 복구 어댑터. 두 번째 pending 저장소나 서버 결과 캐시 없음 |
| `pages/field/FieldCartReview.tsx.txt` | 새 요청/수정/Undo의 표시 채널 연결, 재진입 복구. 확인된 원래 제출과 현재 초안이 일치할 때만 초안 정리 |
| `pages/field/FieldRequestsList.tsx.txt` | Admin 전체 선행 준비본 보존. 본인 수정/취소 재진입 안내를 공통 복구로 연결 |
| `components/admin/AdminRequestActions.tsx.txt` | 재진입 시 공통 원래 의도 복구. 완료 Undo의 원래 operation ID 유지 |

공통 인터페이스:

- `getPendingRequest(target)`: 지정 대상의 현재 문서 소유 작업에 대한
  분리된 의도 사본. `target`은 요청 ID 문자열 또는 새 요청의 `new`.
- `getPendingRequestForChannel(channel)`: 카트/카트 Undo의 폐기된
  패널을 다시 열 때 작업 위치를 찾는 표시용 채널. 서버 키/업무 상태 아님.
- `subscribePendingRequests(listener)`: UI 갱신 알림. 응답 본문 캐시 아님.
- `retryPendingRequest(target, operationId)`: 정확한 현재 작업만 명시적으로
  확인. 조회 결과에 따라 원래 ID·본문으로만 재시도.
- 기존 `requestCommand`의 첫 다섯 인자는 유지한다. 선택적 여섯 번째
  표시 채널을 카트 경로에만 사용한다.

미확정 상태의 화면은 폼/새 처리 버튼을 잠근다. 재진입한 화면이
현재 폼·새로 받은 revision으로 이전 작업의 본문을 다시 만들지 않는다.
동일 계정이 아닌 화면에는 pending 표시/복구를 노출하지 않는다.
서버에서 권한이 철회되면 서버 확인 API의 거절이 우선한다.

### 초안 및 Undo 보존

카트의 재진입 복구가 성공하면 현재 초안의 제출 대상·revision·자재·메타가
원래 제출과 모두 일치할 때만 현재 초안을 정리한다. 다른 초안은 유지하고
아직 제출되지 않았다는 기존 문구를 표시한다.

완료 작업의 Undo는 서버 확인 결과의 revision과 원래 완료 작업 ID를
사용한다. 재진입으로 잃은 일반 상태 변경의 이전 상태를 추측해 역전환
Undo를 만들지 않는다. 카트 Undo도 서버 작업은 확인할 수 있지만,
사라진 이전 로컬 초안/원본 스냅샷을 임의로 복원하지 않는다.
현재 초안 유지 안내를 제공한다. 이는 서버 Undo와 로컬 초안 복원을
구별하기 위한 의도적인 안전 제한이다.

## 3. 검증 방법

최종 결과: **후보 TypeScript 통과, 합성 브라우저 46개 경우,
기존 receipt 서비스의 쿼리 계약 대역 6개 경우 통과.**
브라우저 예외 0건, 예상 밖 외부/합성 요청 0건.
최종 후보 전체에 대해 타입 검사와 브라우저 검사를 다시 실행했다.
앞선 부분 검사나 중간 실행의 경우 수를 합산하지 않았다.

```sh
env -i PATH="$PATH" LANG=C.UTF-8 NODE_ENV=test \
  node development/request-operation-safety/verify.mjs
```

- 기존 설치 의존성만 사용. 자격증명 없는 `/tmp` 소스 작업본.
- 타입 검사는 기존 오프라인 가드 아래 실행하며 네트워크·DB·리스너·
  자식 프로세스 실행을 차단한다.
- 실제 변경 helper/transport/queryClient/feedback/Admin/카트/요청 카드와
  기존 언어·테마·카트 provider를 독립 Chromium에서 사용한다.
- 인증 훅과 라우터는 합성 경계, `fetch`는 합성 HTTP 계약이다.
  모든 외부 브라우저 요청을 차단한다. 서버/포트를 열지 않는다.
- 계정 교체의 `/home` 이동은 합성 빈 문서로만 응답한다.
  실제 로그인 전환을 수행한 증거가 아니다.
- 기존 receipt 서비스는 합성 identity와 쿼리 계약 대역으로 검사한다.
  실제 SQL 실행·트랜잭션·행 잠금·지점 membership 검증이 아니다.
- 최종 검사 수와 경우명은 `results.json`, 후보 및 네 선행 준비본의
  입력 해시는 `manifest.json`에 기록한다. 검사 중 입력/실행 원본의
  해시가 바뀌면 성공 결과를 만들지 않는다.
- 합성 화면은 `generated-artifacts/request-operation-safety/`에 저장한다.
  실제 직원 자료/앱 캡처가 아니다.
- `--checked-work`는 전체 타입 입력 해시가 같은 통과 작업본에만
  타입 검사 재사용을 허용한다. `--case` 부분 검사는 공식 성공 결과를
  생성하지 않는다.

## 4. 통합에 넘기는 순서와 차단 조건

1. 네 기존 준비본과 이번 후보의 기준 해시를 비교한다. 차이가 있으면
   전체 파일 덮어쓰기 대신 변경 부분을 검토한다.
2. 네 준비본 이후 이번 여섯 후보를 통합 작업본에 적용한다.
   공통 context getter/helper와 표시 어댑터를 함께 적용해야 한다.
3. 실제 App/Wouter 중첩 지점 라우팅, 상세 복귀/뒤로·앞으로,
   역할별 연결을 별도 격리 검사한다. 이번 mock router 검사로 대체하지 않는다.
4. 검증 결과를 보존하고 실제 적용 파일·지점·허용 역할·기존 탭/초안/
   미확정 작업 처리·재시작 허용 범위를 명시한 변경목록을 제출한다.
5. 별도 승인 전에는 실행 소스 적용·설정 변경·실제 연결·재시작·배포를 하지 않는다.

## 5. 해결하지 않았거나 보장하지 않는 것

- **새로고침·탭 종료·브라우저 종료·새 문서 이동을 넘는 ID 보존은 없다.**
  개인정보 영속 저장이나 새로운 서버 복구 계약은 승인 범위 밖이다.
  미확정 상태를 초기화하려고 새로고침하거나 재로그인 후 새 제출하지 않는다.
  기존 탭의 미확정 업무는 반영 절차 전에 확인해야 한다.
- 현재 권한으로 결과를 조회할 수 없으면 과거 스냅샷을 우회해서
  표시하지 않는다. 서버 결과가 없는 미확정을 사용자가 임의로 해제하는
  기능도 없다.
- 전체 응답 스키마 재설계, 서버 상태·재고 계산·권한/receipt 정책 변경 없음.
- 실제 로그인·직원 업무·휴대폰·DB/저장소/provider 연결은 미검증이다.
- 기존 시작 설정 테스트 실패와 실제 화면 이동 대기시간은 미해결이다.
- 이번 완료는 수정 준비본과 격리 증거의 완료다. 실제 업무 활성화·
  GitHub push·배포 완료가 아니다.
