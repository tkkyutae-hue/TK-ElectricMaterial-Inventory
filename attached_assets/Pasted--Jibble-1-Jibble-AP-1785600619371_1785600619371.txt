현재 Jibble 출퇴근 동기화 기능에 문제가 있습니다. 아래 내용을 확인하고 기존 기능을 깨뜨리지 않도록 수정해 주세요.

## 현재 문제

### 1. Jibble API 429 Rate Limit

현재 약 15명의 직원을 `Promise.all`로 동시에 조회하고 있습니다.

이 때문에 Jibble API가 HTTP 429 Rate Limit을 반환합니다.

각 요청 실패가 내부에서 `null` 처리되면서 동기화 API 자체는 HTTP 200 성공으로 응답하지만, 실제로는 모든 직원 조회가 실패하여 펀치인 직원 수가 0명으로 저장되는 문제가 있습니다.

### 2. 일부 Jibble personId가 404 반환

데이터베이스에 저장된 일부 `jibblePersonId`가 Jibble 서버에 존재하지 않습니다.

잘못 매핑되었거나 삭제된 Jibble 직원 ID일 가능성이 있습니다.

이 404 오류는 429 또는 일시적인 서버 오류와 별도로 처리해야 합니다.

### 3. 프로덕션 Deployment가 구버전 코드 실행 중

개발 서버에서는 새로운 코드를 실행하고 있어도 Replit Deployment는 별도의 프로덕션 환경입니다.

Deployment 로그에서 기존 `/TimesheetsSummary` 관련 HTTP 500 오류가 계속 보인다면 프로덕션 배포가 아직 구버전 코드를 실행 중인 것입니다.

수정 완료 후 반드시 새로운 Deployment가 필요합니다.

## 필요한 수정 사항

### A. 동시 호출 제거

Jibble 직원 조회에서 `Promise.all`을 제거하고 순차적으로 한 명씩 호출해 주세요.

동시에 실행되는 Jibble API 요청 수는 항상 1개여야 합니다.

각 직원 요청 사이에는 약 300~500ms 정도의 짧은 간격을 넣어 주세요.

### B. 429 재시도 처리

HTTP 429 발생 시 즉시 실패 처리하지 말고 재시도해 주세요.

재시도 조건:

* `Retry-After` 헤더가 있으면 해당 시간을 우선 사용
* 없으면 exponential backoff 적용
* 최대 4회 정도 재시도
* 재시도 대기 시간은 지나치게 길지 않게 제한

HTTP 500, 502, 503, 504와 같은 일시적인 서버 오류도 동일하게 재시도할 수 있습니다.

### C. 기존 펀치인 데이터 보호

429, 네트워크 오류 또는 Jibble 서버 오류로 특정 직원을 조회하지 못했다고 해서 그 직원을 자동으로 펀치아웃 상태로 변경하면 안 됩니다.

조회 결과를 다음과 같이 구분해 주세요.

* 조회 성공: 최신 상태로 업데이트
* 404: 잘못된 Jibble ID로 분류
* 429 또는 서버 오류: 기존 캐시 또는 기존 펀치인 상태 유지
* 모든 직원 조회 실패: 0명으로 저장하지 말고 HTTP 503 반환 및 기존 캐시 유지

일부 직원만 실패한 경우 정상 조회된 직원만 업데이트하고, 실패한 직원의 기존 상태는 유지해 주세요.

### D. 404 잘못된 매핑 처리

Jibble API에서 404가 반환된 직원은 별도 목록으로 수집해 주세요.

관리자 화면에서 다음 정보를 확인할 수 있도록 해 주세요.

* 직원 이름
* 현재 저장된 Jibble personId
* 오류 상태
* Jibble 매핑 해제 버튼

또한 앞으로 새로운 Jibble personId를 저장할 때 실제 Jibble 서버에 해당 직원이 존재하는지 검증한 후 저장해 주세요.

### E. 동기화 결과 로그 및 응답 개선

동기화 결과에 다음 정보를 포함해 주세요.

* 전체 매핑 직원 수
* 조회 성공 수
* 현재 펀치인 수
* 404 수
* Rate Limit 또는 일시적 오류 수
* 기존 상태를 유지한 직원 수

예시 로그:

```text
[jibble-sync] total=15 success=13 punchedIn=6 invalidPersonIds=1 temporaryFailures=1 preserved=1
```

운영 중 새 코드가 배포되었는지 확인할 수 있도록 서버 시작 또는 첫 동기화 시 아래와 같은 버전 로그도 추가해 주세요.

```text
[jibble] active sync strategy: sequential-retry-v2
```

### F. 모든 Jibble 동기화 경로 확인

한 곳만 수정하지 말고 Jibble 동기화가 실행되는 모든 경로를 확인해 주세요.

예상 경로:

* Jibble 연결 직후 초기 동기화
* 관리자가 실행하는 수동 동기화
* 일정 시간마다 실행되는 자동 동기화
* 서버 시작 시 실행되는 동기화가 있다면 해당 경로

모든 경로가 동일한 순차 호출 및 재시도 함수를 사용해야 합니다.

## 검증 조건

수정 후 아래 테스트를 진행해 주세요.

1. 15명을 조회해도 최대 동시 Jibble 요청 수가 1인지 확인
2. 첫 번째 요청이 429이고 다음 재시도에서 성공하는 경우 정상 반영되는지 확인
3. `Retry-After` 헤더가 적용되는지 확인
4. 특정 personId가 404인 경우 다른 직원 동기화가 계속 진행되는지 확인
5. 일부 요청이 실패해도 해당 직원의 기존 상태가 유지되는지 확인
6. 모든 요청이 실패했을 때 펀치인 수가 0명으로 덮어써지지 않는지 확인
7. 관리자 화면에서 잘못된 Jibble 매핑을 해제할 수 있는지 확인
8. TypeScript 검사와 프로덕션 빌드 실행
9. 수정 완료 후 새로운 Replit Deployment 실행
10. Deployment 로그에 아래 문구가 표시되는지 확인

```text
[jibble] active sync strategy: sequential-retry-v2
```
