# TK ELECTRIC — Indiana Phase 2 GitHub 통합 및 공통 코드베이스 구축

## 1. 최종 목표

기존 TK Electric Inventory의 GitHub Repository 하나를 Savannah와 Indiana의 공통 개발 저장소로 사용한다.

**별도의 GitHub Repository를 만들지 않는다.**

기존 저장소:

https://github.com/tkkyutae-hue/TK-ElectricMaterial-Inventory

기존 Replit:

https://replit.com/@tkkyutae/TK-ElectricMaterial-Inventory

최종 운영 구조:

- GitHub `main`: Savannah·Indiana 공통 소스코드
- Savannah: 기존 독립 서버·DB
- Indiana: 신규 독립 서버·DB
- 지점별 차이: 환경변수 및 지점 설정
- 공통 UI·기능: 동일 소스에서 개발
- 지점별 배포: 개별 검증 후 독립 배포

향후 UI나 기능을 수정할 때 동일한 코드를 두 지점에서 다시 개발하지 않아야 한다.

**개발은 한 번, 배포는 지점별로 진행하는 구조를 만든다.**

## 2. 현재 Indiana 개발 결과물 확보

기존 Phase 1·2 결과물을 우선 확인한다.

보고된 경로:

- `/tmp/tk-indiana-phase1.eg8GAs/`
- `/tmp/tk-indiana-phase2.lEwSgc/`
- `/tmp/tk-indiana-preservation-od98ckov/`

이전 보고에 따르면 Phase 2에는 Phase 1 소스가 포함돼 있고, 다음 검사를 재현했다.

- 서버·SQL·HTTP 및 브라우저 통합 검사 23개
- 화면 30개 조합
- TypeScript 오류 0개

해당 결과는 기존 보고값이므로 실제 산출물과 검사 기록을 확인한다.

임시 파일이 사라졌다면 존재한다고 가정하지 않는다.

기존 Savannah 소스를 덮어써서 결과물을 복구하지 않는다.

### 보존 조건

GitHub에 올리기 전에 다음을 검사한다.

- 비밀번호·API Key·DB 접속정보·OAuth Secret 없음
- 세션·쿠키·인증 토큰 없음
- 실제 직원 정보 및 운영 업무 데이터 없음
- DB Dump 및 운영 백업 없음
- 불필요한 node_modules·빌드 결과물 없음
- Savannah 전용 환경 설정과 비밀값이 포함되지 않음

현재 저장소의 공개 여부와 연결된 CI/CD, Webhook, Replit 자동배포 동작도 확인한다.

공개 저장소에 비밀정보가 포함될 가능성이 있거나 Push가 운영 배포를 유발할 수 있다면 Push를 보류한다.

보안 검사를 통과한 소스·테스트·설계 문서만 보존한다.

## 3. Indiana 개발 브랜치 생성

기존 GitHub Repository 내부에 다음 개발 브랜치를 사용한다.

`indiana-phase2`

기존 브랜치가 있다면 상태를 먼저 확인한다.

없다면 현재 기준 커밋과 Phase 2 작업본의 관계를 검증한 뒤 생성한다.

### 브랜치 운영 조건

- `main`은 변경하지 않는다.
- 강제 Push, Reset, 기존 커밋 덮어쓰기 금지
- 기존 Savannah 관련 소스 삭제 금지
- Indiana 작업본의 기준 커밋과 변경 내역 명시
- Phase 1 변경사항이 Phase 2에 포함됐는지 확인
- 실제 빌드 가능한 소스와 테스트를 보존
- 기존 Hosted 설계 문서 포함

보안·자동배포 조건이 충족됐다면 개발 브랜치에 Push할 수 있다.

조건이 충족되지 않으면 안전한 분리 작업본을 유지하고 차단 원인을 보고한다.

**개발 브랜치 Push는 운영 배포 승인이 아니다.**

## 4. 공통 코드베이스 통합

Indiana를 별도 Inventory 프로그램으로 개발하지 않는다.

기존 TK Electric Inventory의 공통 기능을 재사용한다.

공통 관리 대상:

- Login / Authentication
- Branch Selection
- Mode Selection
- Admin Mode
- Field Mode
- Inventory Management
- Item Detail
- Receiving / Issuing / Returning
- Transactions / Transfers
- Material Requests
- Wire Reel Management
- Projects / PO
- Dashboard
- UI Components
- Korean / English / Spanish
- Light / Dark Theme

Savannah와 Indiana에서 같은 화면이나 기능을 별도의 코드로 복제해 유지하지 않는다.

지점별 차이는 `BRANCH_CODE` 등의 명시적 설정으로 처리한다.

기존 구조를 최대한 유지하고, 불필요한 전면 재구성은 피한다.

### 중요

기존 GitHub `main`과 Indiana 개발 소스의 변경사항을 비교한다.

Indiana 코드를 무조건 `main`에 덮어쓰지 않는다.

그동안 Savannah에 적용된 최신 수정사항이 있다면 보존해야 한다.

충돌하는 부분은 기능별로 비교·조정하고, 기준 버전과 수정 근거를 보고한다.

## 5. 지점별 서버와 DB 완전 분리

공통 코드를 사용해도 데이터는 공유하지 않는다.

### Savannah

- 기존 서버 유지
- 기존 PostgreSQL DB 유지
- 기존 세션·인증·저장소 유지
- 기존 재고·거래·릴·PO·가격 유지

### Indiana

- 독립 서버
- 독립 PostgreSQL DB
- 독립 세션 저장소
- 독립 파일·사진 저장소
- 독립 환경 설정

지점 DB 연결은 서버 설정으로만 결정하고, 사용자가 URL이나 요청 파라미터를 조작해 다른 DB에 접근하지 못하도록 한다.

Indiana 서버는 자기 지점의 DB임을 확인하기 전에는 시작 과정의 데이터 작업을 실행하지 않는다.

기존 `server/db.ts`의 PostgreSQL 자동 검색 fallback, seed, migration, backfill, Monday/Jibble 연동 등을 검토한다.

Savannah 운영 DB에 우발적으로 연결되는 경로를 허용하지 않는다.

이번 작업에서 기존 DB 구조나 데이터를 변경하지 않는다.

**TK ELECTRIC INVENTORY**

→ Branch Selection

→ Field Mode / Admin Mode

→ 선택한 지점의 Inventory 화면

Branch Selection:

- Savannah
- Indiana
- Central Management

Central Management는 현재 아이콘과 Coming Soon 화면만 유지한다.

Indiana 개발 환경에서는 Indiana로 진입할 수 있게 한다.

Savannah 운영 연결은 별도 승인 전까지 실제 호출하지 않는다.

기존 계정·권한 구조를 유지하되, 지점별 접근권한을 서버에서 검증할 수 있도록 설계한다.

공통 로그인 UI와 실제 SSO가 동일한 것은 아니므로, 실제 인증 연결이 미완료인 경우 완료로 보고하지 않는다.

## 7. 공통 품목 표준화 구조 보존

모든 지점은 동일한 Master Item에 대해 동일한 정보를 사용해야 한다.

- Global Master Item ID
- SKU
- Item Name
- Category
- Specification
- Size
- Unit of Measure
- 승인된 공통 기준정보

향후 중앙 관리에서 SKU·품목명·규격·사이즈를 변경하면 모든 지점에 동일하게 반영할 수 있어야 한다.

현재 Central Management는 Coming Soon 상태이므로 실제 중앙 동기화는 구현하지 않는다.

기존 Phase 1·2에서 개발된 품목 ID 연결·버전 검증·허용 필드 처리 기반을 유지한다.

중앙 품목 변경으로 기존 재고 수량, 구매가격, 릴, 입출고·PO 이력을 변경하지 않는다.

## 10. 최종 `main` 통합 준비

최종 목표는 검증된 Indiana 및 공통 지점 지원 코드를 기존 `main`에 병합하는 것이다.

다만 이번 작업에서는 아래 조건을 충족한 뒤 통합 가능한 Pull Request 또는 검토 가능한 diff까지만 준비한다.

- 변경 파일과 공통 코드 영향 범위 확인
- Savannah 회귀 검사 통과
- 지점별 환경 분리 확인
- 보안 검사 완료
- 자동배포·Webhook 영향 확인
- 기존 Savannah 데이터 변경 없음
- 코드 되돌리기 방법 준비

**실제 `main` 병합과 운영 배포는 최종 보고 후 별도로 승인받는다.**

개발 브랜치를 영구적인 Indiana 전용 코드베이스로 운영하지 않는다.

향후 Indiana 개발 기능은 공통 코드 원본에 통합하고 지점별 배포 설정으로 구분한다.
