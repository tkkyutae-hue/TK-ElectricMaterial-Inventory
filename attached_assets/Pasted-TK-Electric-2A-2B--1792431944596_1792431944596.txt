TK Electric — 조회 권한·구매가격 보호 통합 작업
2A + 2B 구현·통합 검증 일괄 승인

이번에는 계획만 제출하고 멈추지 마라.
아래 승인 범위 안에서 분리된 작업본의 구현 → 검사 → 발견한 문제 보완 → 통합 검증까지 진행하고, 최종 결과를 한 번에 보고해라.

함수·파일·테스트마다 중간 승인을 요청하지 마라.
이미 합의된 정책이나 소스로 확인할 수 있는 기술적 판단을 다시 사용자에게 묻지 마라.

실제 실행 프로젝트 반영·재시작·배포·기존 DB 작업은 이번 승인에 포함하지 않는다.

────────────────────
1. 작업 방식과 승인 경계
────────────────────

현재 커밋과 미커밋 상태를 확인하고, 실행 중인 프로젝트와 분리된 임시 작업본에서만 수정·검증해라.

- 실제 프로젝트 파일과 실행 중인 서버가 감시하는 파일은 변경하지 않는다.
- 기존 dev/prod DB, 실제 세션 저장소, 업무 API에 접근하지 않는다.
- 앱 시작·재시작, Preview 조작, 배포, 커밋·push·강제 동기화는 하지 않는다.
- 패키지 설치·업데이트, DB 구조·환경·포트·인증 설정 변경은 하지 않는다.
- 소스에 포함된 자격증명이나 직원·업무 데이터를 테스트에 사용하지 않는다.
- GET 요청과 앱 시작에도 자동 쓰기가 있을 수 있으므로 실제 실행을 읽기 전용 검사로 취급하지 않는다.

기존 도구와 합성 데이터로 실제 수정 코드를 검증해라.
실행 가능한 부분은 계속 진행하고, 격리할 수 없는 검사만 미검증으로 남겨라. 안전 제한을 완화해서 검사를 통과시키지 마라.

────────────────────
2. 기존 2A 수정안을 통합해라
────────────────────

기존 2A는 임시 수정안에서 17개 사례를 검사했고 실제 프로젝트에는 미적용으로 보고됐다.

기존 결과물:
- /tmp/tk-2a-routes.proposed.ts
- /tmp/tk-2a-request-list-check.cjs
- /tmp/tk-2a-results.json
- /tmp/tk-2a-route.before.txt
- /tmp/tk-2a-route.after.txt

파일 존재와 기준 소스를 먼저 확인해라.
없거나 현재 소스와 달라졌다면 그 사실을 밝히고, 필요한 경로만 다시 대조해라. 과거 routes.ts 전체를 현재 파일에 덮어쓰지 마라.

2A에서 보존할 동작:

- GET /api/field/requests는 현재 계정의 활성 상태와 세션 ID 일치를 확인한 뒤 목록을 조회한다.
- 미로그인·삭제·비활성 계정은 목록 저장소 호출 전에 거절한다.
- 계정 조회 실패를 undefined 필터나 전체 목록 조회로 연결하지 않는다.
- 이전 req.user에 관리자 정보가 남아 있어도 최신 계정 확인 실패를 우회할 수 없다.
- staff는 검증된 본인 ID로만 요청 목록을 조회한다.
- 쿼리의 사용자 ID나 전체 조회 요구로 범위를 확대할 수 없다.
- admin/manager의 정상 조회와 다른 기존 역할의 확인된 조회 범위를 유지한다.
- 내부 예외·SQL·비밀값을 오류 응답에 그대로 반환하지 않는다.

공용 인증 체계나 관련 없는 API를 전면 개편하지 마라.
기존 2A를 다시 별도 과제로 반복하지 말고 이번 통합 패치에 포함해라.

────────────────────
3. 2B 구매가격 비공개를 구현해라
────────────────────

확정 정책:

- 구매단가·구매금액·공급사 견적의 열람 권한은 활성 admin/manager에게만 있다.
- staff/viewer/manager_viewer에게는 이번 범위의 서버 응답에서 구매가격을 제공하지 않는다.
- manager_viewer라는 이름만으로 가격 권한을 부여하지 않는다.
- 기존 역할 자체를 삭제하거나 다른 업무 권한을 임의로 바꾸지 않는다.
- 일반 자재명·규격·사진·재고량과 정상 요청 조회는 유지한다.

화면에서만 숨기지 말고 서버 응답을 보호해라.

기존 API 대조표를 재사용하되 현재 소스에서 달라진 부분과 미확인 부분을 보완한다. 대상은 다음과 같다.

- 품목 목록·상세 및 상세에 포함된 거래
- 거래 목록·구형 조회 별칭과 중첩 item
- 위치별 재고 잔액의 중첩 item
- 대시보드의 원가 기반 집계
- 프로젝트 목록·상세·최근 거래
- 현장 품목·분류 후보 응답
- 요청·초안 응답과 내부 직렬화 JSON

unitCost, unitCostSnapshot, lastUnitCost, totalValue 등 실제 존재하는 가격 필드·집계·파생값을 확인하고 해당 응답 경로를 보호해라. 필드가 없으면 없다고 기록해라.

구현 조건:

- 권한 없는 응답에서 가격을 제외하되 실제 DB의 가격을 삭제하거나 0/null로 바꾸지 않는다.
- 중첩 객체와 직렬화 JSON 내부의 가격도 확인한다.
- amount/value 같은 이름을 전부 가격으로 간주해 일괄 삭제하지 않는다.
- 응답을 가공할 때 원본·공유 객체를 변경하지 않는다.
- 계정 확인 실패나 남아 있는 관리자 객체로 가격 권한을 부여하지 않는다.
- 가격 보호를 위해 일반 직원의 자재 조회 전체를 막지 않는다.
- 기존 캐시·응답 재사용 때문에 관리자용 가격 응답이 다른 역할에 재사용되는지도 관련 경로에서 확인한다.

가격 필드가 빠져 화면이 깨지거나 비공개 가격을 0원으로 표시한다면 필요한 최소 표시·타입 처리까지 이번 범위에서 수정해라.

이는 디자인 개편 승인이 아니다.
기존 세 언어·두 테마·카테고리 사진·작성 중 입력을 유지한다.

────────────────────
4. 범위를 넓히지 마라
────────────────────

이번 작업은 2A와 위에 명시한 2B 응답 보호다.

다음은 별도 보류한다.

- 2C 배정 PO·다른 팀 업무 조회 범위 제한
- #620 선택창 오류, 공통 Select, ResizeObserver 진단, ErrorBoundary
- Vite 설정 병합안의 실제 적용
- 실제 입출고·릴 저장, 반납 상한, 예약/FIFO, 거래 취소·Undo 로직
- RMS 질문·구현, 견적 모듈 개편
- 내보내기·첨부파일 전체 감사
- 데일리리포트 상세 설계, 라벨·QR, 전체 디자인 개편

2C의 PO 배정 근거가 부족해도 2A·2B는 계속 진행한다.
일별 인력 배정을 지속적인 PO 접근권한으로 임의 해석하거나 새 배정 테이블을 만들지 마라.

범위 밖 가격 경로가 발견되면 잔여 위험으로 기록한다.
이를 이유로 보류 모듈 전체를 재개하거나 “모든 가격 노출 차단 완료”라고 표현하지 마라.

────────────────────
5. 구현과 통합 검증을 끝까지 진행해라
────────────────────

설명용으로 비슷한 로직을 다시 만든 테스트만으로 끝내지 마라.
실제 수정 대상 라우트·권한 분기·응답 처리 코드를 실행하고, 계정 조회·DB·세션·업무 저장소 경계만 대역으로 분리해라.

필수 검증:

A. 2A 보호
- 미로그인·삭제·비활성·계정 조회 실패 시 업무 목록 조회 없음.
- 이전 관리자 정보가 남아 있어도 확인 실패 시 거절.
- 정상 staff는 본인 요청만 조회.
- 쿼리 조작으로 타인·전체 조회 불가.
- 기존 관리자 및 다른 역할의 정상 동작 유지.

B. 2B 보호
- 활성 admin/manager는 허용된 가격과 기존 응답 유지.
- staff/viewer/manager_viewer의 응답에는 대상 가격이 없음.
- 중첩 item·거래·집계·직렬화 JSON에도 대상 가격이 없음.
- 계정 미확인·비활성·역할 미확인으로 가격 권한이 부여되지 않음.
- 일반 자재 정보와 정상 요청·초안 조회는 유지.
- 비공개 가격을 실제 0원으로 표시하지 않음.
- 원본 응답 객체가 변하지 않음.
- 역할별 연속 조회나 계정 상태 변경으로 이전 가격 권한이 재사용되지 않음.

C. 통합 회귀
- 2A와 2B를 함께 적용한 작업본으로 검사.
- 2B 변경이 2A의 계정 확인 실패 차단을 되돌리지 않음.
- 기존 실제 재고 변경 권한과 요청·초안 보호를 약화시키지 않음.
- 필요한 타입·구문 검사 수행. 기존 오류와 이번 변경으로 생긴 오류를 구분.
- 화면 처리를 변경했다면 실제 관련 컴포넌트·CSS와 합성 데이터로 검사.
  브라우저 검사는 업무 요청·외부 네트워크를 차단하고 실제 앱을 열지 않는다.

테스트에서 승인 범위 안의 문제가 발견되면 수정하고 필요한 검사만 다시 실행해라.
그때마다 사용자에게 승인받지 마라.

기존 17개 검사를 이유 없이 반복하지는 않되, 통합 후 회귀 확인에 필요한 재실행은 수행한다.

6. 멈춰야 하는 경우
────────────────────

다음 경우에는 해당 부분만 멈추고 이유를 기록한다.

- 새로운 업무 정책 결정이 필요한 경우.
- 실제 DB·실행 환경·패키지·보안 설정 변경 없이는 진행할 수 없는 경우.
- 이번 범위 밖의 기능 변경이 필요한 경우.

독립적으로 진행 가능한 구현·검증은 계속해라.
기술적 구현 방법, helper 구성, 테스트 도구 조정 같은 내부 판단을 사용자에게 하나씩 넘기지 마라.
