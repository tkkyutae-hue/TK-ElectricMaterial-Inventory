# TK ELECTRIC — Multi-Branch Inventory System
## Phase 1: Indiana Branch 구축 및 공통 품목 표준화 기반

### 1. 프로젝트 목표

현재 운영 중인 **[TK Electric] Material Inventory**를 기준으로 Multi-Branch Inventory System을 구축한다.

이번 개발에서는 **Indiana Branch만 새로 구축한다.**

기존 Savannah 앱과 데이터는 그대로 유지한다. Central Management는 향후 개발을 위한 메뉴 아이콘과 준비 화면까지만 만든다.

최종적으로는 다음 구조를 목표로 한다.

- 하나의 공통 Inventory 소스코드
- 지점별 독립 서버 및 PostgreSQL DB
- 동일한 UI, 기능, 디자인
- 회사 전체에 통일된 SKU, Item Name, Category, Specification, Size, Unit
- 향후 중앙에서 품목 정보를 변경하면 모든 지점에 동일하게 반영
- 지점별 독립 재고 수량, 구매가격, 입출고 이력, 릴, 프로젝트 및 PO

**기존 TK Electric Inventory 기능을 새로 개발하거나 별도의 유사 앱으로 재구현하지 마라. 기존 코드를 최대한 재사용한다.**

기존 Savannah 로그인과 운영 라우팅은 변경하지 않는다.

### 5. 모든 지점의 품목 정보 표준화 — 필수 아키텍처

**이 항목은 향후 중앙 시스템을 만들 때 반드시 구현해야 하는 핵심 조건이다.**

Savannah, Indiana 및 향후 추가될 모든 지점은 동일한 품목에 대해 아래 정보가 일치해야 한다.

- Global Master Item ID
- SKU
- Item Name
- Category
- Subcategory
- Detail Type
- Subtype
- Specification
- Size / Size Label
- Material / Rating
- Unit of Measure
- 공통 Manufacturer / Model 정보
- 공통 Product Images
- 공통 분류·검색 기준

예를 들어 동일한 자재가 Savannah에서는 `3/4" EMT`, Indiana에서는 `EMT PIPE 0.75"`처럼 서로 다른 표준 품목명으로 등록되지 않게 한다.

동일한 Master Item을 참조하는 지점 품목은 같은 SKU·자재명·규격·사이즈를 사용해야 한다.

각 지점에서 공통 품목 정보를 임의로 변경할 수 없도록 설계한다.

#### 공통 품목 식별

각 품목에 변하지 않는 Global Master Item ID를 사용한다.

각 지점의 기존 Local Item ID는 별도로 유지한다.

예시:

Global Master Item ID: `MASTER-000125`

Savannah Local Item ID: `125`

Indiana Local Item ID: `38`

공통 품목 ID로 동일성을 식별하고, 지점별 Local Item ID는 거래·릴·프로젝트 연결을 위해 유지한다.

SKU나 품목명을 변경하더라도 기존 Local Item ID 및 과거 거래 관계를 재번호하거나 삭제하지 않는다.

이번 개발에서 실제 중앙 Master DB를 만들지는 않는다. Indiana는 향후 공통 품목 ID와 연결할 수 있는 데이터 구조를 준비한다.

기존 Savannah 품목에 공통 ID를 실제로 추가하거나 매핑하는 작업은 이번 범위 밖이다.

### 6. 향후 중앙 품목 변경 시 전 지점 업데이트 — 필수 설계

**중앙에서 공통 품목 정보를 변경하면 모든 지점의 현재 품목 정보가 동일하게 업데이트되어야 한다.**

예시:

중앙에서 다음 품목을 수정한다.

기존 SKU: `EMT-075-OLD`

신규 SKU: `EMT-075`

기존 Item Name: `3/4 EMT PIPE`

신규 Item Name: `EMT CONDUIT 3/4 IN`

이 경우 향후 중앙 동기화 시스템이 작동하면:

- Savannah의 해당 품목 SKU와 표시명이 변경된다.
- Indiana의 해당 품목 SKU와 표시명이 변경된다.
- 향후 추가된 지점도 동일하게 반영된다.
- 기존 재고 수량은 유지된다.
- 실제 구매가격은 유지된다.
- 입출고 거래 관계와 릴 기록은 유지된다.
- 과거 거래의 가격·규격 스냅샷은 수정하지 않는다.

**변경되는 것은 승인된 공통 품목 기준정보이며, 지점별 재고·거래 데이터가 아니다.**

#### 변경 규칙

1. 중앙에서 승인한 품목 변경만 지점에 전달한다.
2. 각 지점은 동일한 Master Item ID를 기준으로 업데이트한다.
3. 변경 버전과 적용 시각을 기록한다.
4. 같은 변경이 반복 전송돼도 중복 품목을 생성하지 않는다.
5. 오래된 버전이 최신 정보를 덮지 못한다.
6. 일부 지점 적용이 실패하면 미반영 상태를 기록하고 안전하게 재시도한다.
7. 재전송 또는 DB 복구 이후에도 기존 재고·거래를 초기화하지 않는다.
8. SKU 변경 시 기존 SKU 별칭과 외부 참조 호환성을 고려한다.
9. 다른 품목과 SKU 충돌이 발생하면 자동으로 덮어쓰지 않는다.
10. 과거 거래의 품목 식별·규격·수량 의미를 훼손하지 않는다.

#### 변경 제한

단순 이름·표기 수정과 실제 자재 규격 변경은 구분한다.

예를 들어 `3/4 IN` 자재를 실제로 `1 IN` 자재로 바꾸거나 EA를 FT로 변경하면 기존 재고 수량의 의미가 달라질 수 있다.

이런 변경은 일반 동기화로 즉시 적용하지 않는다. 새로운 품목 등록 또는 별도 승인된 데이터 전환 절차가 필요하다.

**이번 Phase 1에서는 실제 중앙 동기화를 구현하거나 실행하지 않는다.**

다만 Indiana의 데이터 모델과 품목 처리 구조는 향후 위 기능을 추가할 수 있도록 설계하고, 합성 데이터로 동일 ID 매핑 및 허용 필드 업데이트 규칙을 검증한다.

### 7. Indiana Branch Inventory 개발

Indiana는 기존 TK Electric Inventory 소스와 기능을 재사용한다.

다음 모듈을 유지한다.

- Inventory Management
- Item Detail
- Admin Mode
- Field Mode
- Receiving
- Issuing
- Returning
- Transfers
- Transactions
- Wire Reel Management
- Material Requests
- Projects / PO
- Dashboard
- User Roles & Permissions
- 기존 언어 및 테마 지원

Indiana 전용 독립 개발 서버와 독립 PostgreSQL 개발 DB를 사용한다.

기존 Savannah 데이터를 복사해 사용하지 않는다.

Indiana 개발 DB는 승인된 기준정보 또는 합성 데이터로 구축한다.

실제 Savannah 품목 목록이 필요한 경우 사용 승인이 확인된 기존 Export 자료를 이용한다.

그러한 자료가 없다면 합성 품목으로 진행한다.

운영 데이터 추출을 위해 Savannah DB에 임의 접속하지 않는다.

### 8. Indiana 초기 재고 상태

Indiana는 새 지점이므로 기존 Savannah 업무 기록을 가져오지 않는다.

초기 데이터 기준:

| 항목 | Indiana 최초 상태 |
|---|---|
| 공통 품목 정보 | 승인된 기준정보 또는 합성 데이터 |
| 재고 수량 | 0 |
| 위치별 재고 잔액 | 0 |
| 실물 릴 기록 | 없음 |
| 입출고·반납 이력 | 없음 |
| 예약 기록 | 없음 |
| 자재 요청·초안 | 없음 |
| PO·프로젝트 업무이력 | 없음 |
| 실제 구매가격·거래금액 | Savannah에서 복사하지 않음 |

필요한 창고 위치·카테고리 등 기본 설정은 새 Indiana 환경용으로 별도 구성한다.

**기존 Savannah DB를 복제한 뒤 재고 숫자만 0으로 만드는 방식은 금지한다.**

Indiana에서 실제 입고를 기록하면 Indiana 재고만 변경돼야 한다.

Savannah 재고·거래 데이터에 영향을 주지 않아야 한다.

### 9. Indiana 품목 등록 화면

기존 Item Management UI를 재사용한다.

향후 중앙 관리 도입을 고려해 다음 업무 흐름을 목표로 한다.

**품목 검색**

↓

**공통 품목에 있는가?**

- 이미 존재: 해당 품목 사용
- 중앙에 없는 신규 품목: 중앙 등록 요청

↓

**중앙에서 승인**

↓

**전 지점 품목 정보 반영**

하지만 이번에는 Central Management가 미구현이므로 실제 중앙 등록 요청이나 승인 API를 작동하는 기능처럼 제공하지 않는다.

Indiana에서는 승인된 기준 품목 또는 합성 품목만 사용하는 개발 환경을 먼저 완성한다.

추후 중앙 도입 시 기존의 자유로운 품목 생성·수정 권한을 중앙 승인 흐름으로 대체할 수 있도록 설계한다.

중앙이 아직 없는 상태에서 임의의 지점별 정식 SKU를 생성해 두 지점의 표준이 달라지게 만들지 않는다.

개발 테스트용 임시 품목은 운영용 승인 품목과 명확하게 구분한다.

### 10. 가격 관리 — 이번 개발 제외

이번 Phase 1에서는 중앙 가격 관리 기능을 만들지 않는다.

기존 구매가격 조회·저장 로직을 변경하지 않는다.

Savannah 구매가격을 Indiana로 복사하지 않는다.

중앙 승인단가를 새로 생성하지 않는다.

기존 2A·2B 수정안이 개발됐거나 검사됐다는 이유로 이번 작업에 자동 적용하지 않는다.

중앙 가격 관리는 추후 별도 프로젝트 범위로 진행한다.

RMS 및 자동 구매 기능도 보류한다.

### 11. 공통 코드와 디자인 관리

**Savannah와 Indiana는 동일한 Inventory 소스를 기준으로 개발되어야 한다.**

두 지점의 UI나 기능을 독립적으로 다시 작성하지 않는다.

장기 목표는 다음과 같다.

1. 공통 기능 수정은 한 코드베이스에서 수행한다.
2. Admin Mode 및 Field Mode 디자인도 공통 컴포넌트로 관리한다.
3. 지점별 DB 설정과 실행 환경은 분리한다.
4. 각 지점은 공통 코드의 특정 검증 버전을 배포한다.
5. 지점별 특수 설정은 제한적인 환경 설정으로 분리한다.
6. 수정한 공통 기능은 동일 코드를 두 지점에 배포할 수 있어야 한다.

기존 GitHub 저장소를 기준으로 공통 모듈 및 Indiana 설정 구조를 설계한다.

이번 개발을 이유로 기존 Savannah의 실행 소스를 직접 변경하거나 GitHub main에 자동 병합·push하지 않는다.

기존 소스와 분리된 작업본에서 구현·검증한 뒤 통합 방식을 보고한다.

- 지점 선택 후 기존 Mode 선택
- 역할별 접근 검사
- 기존 Savannah 운영 앱 변경 없이 개발 환경에서 검증

**Step 4 — 향후 공통 품목 동기화를 위한 구조 준비**

- Global Master Item ID 구조
- Local Item ID 유지
- 공통 SKU / Name / Size / Specification / Unit 정책
- 향후 중앙 변경 버전 처리에 필요한 인터페이스
- 공통 품목 필드와 지점 전용 필드 분리
- 재고·거래 보존 검증

**Step 5 — 통합 검증**

- Indiana Inventory 기능 정상 동작
- Field Mode / Admin Mode 유지
- 지점 선택 및 모드 전환
- 계정·지점 권한 차단
- 품목 ID 연결 구조
- 허용된 공통 정보 변경 시 지점 데이터 보존
- 기존 Savannah 소스·DB·배포 미변경 확인

**중앙 품목 CRUD, 실제 중앙→지점 자동 동기화, 중앙 승인 및 Savannah 연결은 후속 Phase다.**

### 13. 기존 데이터 보호 — 절대 조건

Savannah에서 이미 사용 중인 데이터는 변경하지 않는다.

보호 대상:

- Item ID / SKU
- Stock Quantity
- Location Balance
- Wire Reel ID / Length
- Transaction History
- Project / PO
- Material Request / Draft
- Actual Purchase Price
- Supplier Records
- User Accounts
- Photos / Attachments

이번 신규 개발을 위해 기존 데이터를 삭제·병합·재번호·재계산하지 않는다.

기존 Savannah의 DB 접속, seed, migration, backfill, 서버 재시작 및 배포는 승인하지 않는다.

기존 Inventory의 시작 스크립트에 자동 데이터 변경 작업이 있으면 Indiana에서 재사용하기 전에 대상 DB 및 안전성을 확인한다.

실행 환경 분리를 확인할 수 없으면 실제 DB 실행을 멈추고 독립 테스트 환경에서 계속 개발한다.

### 14. 최종 완료 기준

다음 항목이 확인되면 Phase 1 완료로 보고한다.

- 로그인 → 지점 선택 → 모드 선택 흐름의 개발 환경 구현
- Central Management 아이콘 및 Coming Soon 화면
- 공통 품목 ID 및 통일된 SKU·품목명·사이즈 정책

- 합성 데이터 기반 공통 필드 업데이트 및 지점 데이터 보존 검사

- 기존 Savannah 운영 환경 미변경

이번에 중앙 DB가 없으므로 **실제 전 지점 자동 품목 업데이트는 미구현으로 보고**한다. 미래 기능을 현재 완료된 것처럼 표시하지 않는다.

### 15. 개발 및 최종 보고 지침

승인된 Indiana 개발 범위에서는 소스 확인, 코드 구현, 격리 검증 및 기술적인 문제 보완을 한 번에 진행한다.

사소한 구현 결정마다 사용자에게 승인을 요청하지 않는다.

다음 작업은 별도 승인이 필요하다.

- Savannah 기존 앱 또는 DB 변경
- 운영 배포·재배포
- 기존 데이터 마이그레이션
- 중앙 서버·DB 신규 생성
- 실제 중앙 동기화 실행
- 유료 서비스·패키지 추가
- 기존 인증정보·보안 설정 변경

최종 보고에는 다음을 포함한다.

1. 실제 재사용한 기존 Inventory 소스 및 기준 버전
2. Indiana 프로젝트와 기존 앱의 코드 공유 방식
3. 구현한 화면과 기존 기능 유지 여부
4. 새 Indiana DB의 독립성
5. 공통 SKU·품목명·규격·사이즈 관리 구조
6. 향후 중앙 업데이트가 전 지점에 반영되는 기술적 설계
7. 실제 검사 결과와 미구현 기능
8. 기존 Savannah 앱·DB·배포 미변경 여부
9. 다음 Phase에서 중앙 관리 기능을 구현할 때 필요한 작업

**최종 개발 원칙**

One Shared Inventory Codebase.

One Standard Item Definition.

Independent Branch Servers and Databases.

Central Management UI Placeholder Only in Phase 1.

Indiana Branch Development Only.

Preserve All Existing Savannah Data.
